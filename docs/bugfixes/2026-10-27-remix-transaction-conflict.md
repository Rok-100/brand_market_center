# Bugfix：切片审核并发保存冲突

- 分支：`codex/bugfix-remix-transaction-conflict`
- 跟踪：[Issue #3](https://github.com/Rok-100/brand_market_center/issues/3)
- 日期：2026-10-27

## 现场问题

本地自动混剪已完成三条来源准备并生成或复用切片，在切片审核处理到 8/33 时出现 `Document changed during transaction`。任务进入失败状态，页面错误归类为外部权限或配置问题。

## 代码层面的缺陷

原文件兼容适配器按路径共享最近观察到的文档版本，写入时没有固定业务修改最初读取的版本。页面进度刷新、缓存水合与审核保存交错时，这个共享版本会变化。业务层还长期缓存解析后的素材库，无法保证它与适配器最近观察到的版本属于同一快照。

因此必须修正快照与提交版本的绑定，不能简单以最新版本重发旧文档，也不能取消存储网关的版本检查。本次针对这类交错增加确定性回归测试；现场最初冲突的具体并发写入方未通过历史日志唯一确认。

## 修复

1. 元数据适配器增加内部文档事务能力，读取时返回权威数据、版本和哈希；提交显式使用该快照版本，继续由 MySQL 执行 CAS 检查。
2. 来源进度刷新与新事务按同一路径排队，避免缓存读取和事务提交交错修改内部版本状态。大文档增量从本次快照字节计算，不依赖后来更新的本地缓存。
3. 二创素材库更新基于权威快照计算修改一次。发生 CAS 冲突时最多提交三次，只三方合并互不冲突的字段或相同结果，不重新执行 updater、识别、审核、生成或回传副作用。
4. 同字段冲突，以及来源依据、授权、任务暂停、归档、所有人、产品或框架变化，拒绝合并旧结果，交回业务流程重新核验。
5. 重试耗尽后保留原批次、已有素材、审核回执和已完成计数，进入带退避的原批次续跑，并显示存储冲突原因。恢复回执本身再遇冲突时也有进程内冷却，避免立即重试热循环。
6. 启动时恢复此前因该存储错误进入 error 的授权任务，沿用原批次；不自动唤醒用户暂停或已归档任务。

## 本地部署实测

按项目约定重新生成配置、执行权限初始化、重建二创镜像并更新服务；存储网关健康。现场原燕窝面膜任务使用同一 run ID 从失败状态恢复：

- 切片审核由原先的 8/33 推进到 33/33，其中通过 31 条、退回或跳过 2 条。
- 原批次状态变为 `completed`，错误信息清空，生成 1 条审核通过的成片。
- 恢复期间并发读取页面进度 30 次，全部返回 HTTP 200，服务日志未再出现本次事务冲突。
- 来源仍为 3 条、切片仍为 66 条，没有通过重新分配批次或重复创建切片规避原失败。

这些结果验证了本次现场恢复和测试中的交错场景，不代表任意外部并发写入或不同素材内容都能自动合并或通过审核。

没有修改 MySQL CAS 校验，没有删除数据卷或替换用户素材，也没有取消产品版本/来源凭证要求。候选与素材内容不满足其他门禁时仍可正常受阻；该修复不等于任何输入都能生成成片。
