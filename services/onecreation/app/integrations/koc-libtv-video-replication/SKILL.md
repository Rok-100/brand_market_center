# KOC LibTV 视频复刻

## 目的

使用此技能，将一份 KOC 产品视频翻拍需求转化为可复用资产、稳定的逐片段提示词、LibTV 画布工作以及经过验证的视频输出。对于中文 KOC“双人唠嗑”、居家 Vlog、护肤/美妆种草、产品替换以及 Seedance/LibTV 生成任务，优先使用此技能。

在创建或更新提示词文档时，如需了解详细的输入/输出约定和提示词字段，请阅读 `references/io-contract.md`。

## LibTV CLI 身份验证规则

进行任何 LibTV 操作之前，先运行 `libtv account info`。仅在返回 401、“未登录”或凭据无效时执行登录：

1. 直接运行 `libtv login web --open`，让 CLI 使用系统默认方式打开登录页，并等待命令完成。不要手动提取回调 URL，不要调用浏览器控制工具，也不要要求特定浏览器。
2. 登录命令成功后，再运行 `libtv account info` 验证身份。
3. 只有当 `libtv login web --open` 失败、超时或回调异常时，才通知用户人工关闭系统代理/VPN，然后重试同一命令。不要在登录正常时预先要求用户关闭代理，也不要自动修改用户的代理设置。
4. 用户关闭代理后仍无法完成网页登录时，再回退到 `libtv login phone`；向用户索取手机号并按短信验证码两步流程登录。
5. 所有登录尝试结束后都使用 `libtv account info` 复核；验证失败则停止后续上传或生成并报告阻塞项。

## 任务顺序覆盖规则

对于 KOC 翻拍任务，即使较早的项目文件夹中已经包含看似可以复用的资产，也要使用以下顺序规则：

- 在创建第一个本地文件之前，先获得或让用户指定当前任务的 `<task_asset_root>`。产品图和人物图可以稍后补充，但任务根目录不能推迟；所有后续数据都必须写入该目录。
- 将对原始参考素材的深度拆解视为第一个必需交付物。将其保存为 `<task_asset_root>/analysis/deep_dive/<product>_<chat_format>_original_reference_deep_dive.md`，并在与用户的对话中呈现深度拆解的关键内容。仅有聊天内笔记是不够的。
- 在当前任务选定的人物场景和产品资产得到确认之前，不要预先复制、锁定或暗中复用旧项目中的产品图片或人物场景图片。如果用户表示这些资产图片可以稍后提供，则只在 `<task_asset_root>` 中处理参考视频/音频和深度拆解，直到用户补齐资产。
- 如果用户要求在编写提示词之前将参考音频放入本地资产文件夹，则只把处理后的参考音频复制到该处，并记录路径/哈希。产品资产和人物资产的锁定应留待在选定的本地资产文件夹中完成。
- 用户提供选定的人物场景图片和当前任务资产文件夹后，使用以下内容构建新的视频提示词包：已保存的原始参考素材深度拆解、准确无误的新口播脚本、选定的人物场景图片、处理后的参考音频，以及该本地文件夹中的产品资产。
- 输出新视频提示词供用户确认时，在同一回复/提示词包中包含一份已就绪可供提示词使用的资产审计：选定的人物场景、产品资产、参考音频、可用时的哈希、每个片段的必需资产，以及产品露出的分镜编号。
- 用户确认提示词包后，在进行任何 LibTV 上传或生成之前，再次执行最终的“脚本已确认”本地资产复查。

## 统一任务资产目录

将用户提供的“当前任务本地资产文件夹”记为 `<task_asset_root>`，并将它作为该任务全部源素材、标准资产、中间产物、日志和最终产物的唯一根目录。不要再把任务文件散落到工作目录下的 `prep/`、`outputs/` 或其他旧项目目录。

```text
<task_asset_root>/
├── source/                         # 原始参考视频、图片、脚本和用户输入
├── assets/
│   ├── character_scene/
│   │   ├── candidates/             # 50% / 60% / 70% 三张候选图
│   │   └── selected/               # 用户最终选定的人物场景图
│   ├── product/                    # 产品正面、顶部、包装等标准资产
│   └── reference_audio/            # 主音频、逐片段变体及同步副本
├── analysis/
│   ├── deep_dive/                  # 原片深度拆解
│   └── frames/                     # 抽帧、关键动作帧和视觉检查图
├── prompts/                        # 提示词 Markdown、片段计划 JSON、审计记录
├── intermediate/                   # 转码、临时拼接清单、清单和可追踪中间文件
├── libtv/
│   ├── logs/                       # 登录以外的 create/upload/run/query 结果
│   └── state/                      # 画布、节点、模型和执行状态记录
└── outputs/
    ├── clips/                      # 已下载并验证的逐片段视频
    └── final/                      # 全片拼接预览和最终交付视频
```

- 在首次获得 `<task_asset_root>` 后创建所需子目录；只创建当前任务实际需要的目录。
- 将工具产生的任何可复用临时文件移入 `intermediate/` 或相应分类目录，并在清单中记录。任务交付物不得只存在于系统临时目录、远程节点或技能目录中。
- 技能自带的可复用脚本保留在本技能的 `scripts/` 中；脚本运行产生的数据和日志必须写入 `<task_asset_root>`。
- 所有文档、JSON 和日志中的路径都使用 `<task_asset_root>` 下的实际绝对路径。

## 必需输入

在生成前收集或推断以下内容：

- 源风格参考：视频 URL、本地视频、截图或用户提供的参考图片。完整复刻工作流必须具备此项；只有在用户明确要求无参考初稿时才可省略。
- 唠嗑形式：用户应指定 `单人唠嗑` 或 `双人唠嗑`；如果未指定，则根据源资产/参考视频推断，并在编写提示词之前说明该假设。
- 候选生成模式：固定生成三张全新的人物场景候选图，相似度分别为 `50%`、`60%` 和 `70%`。候选图片是生成流程中的检查点，不是用户提供的输入。
- 选定的人物场景图片：用户必须从候选图中准确选择一张，下载/保存到本地资产文件夹，然后将其报告给当前执行 Agent，作为后续持续使用的人物身份/场景基准。
- 当前任务的本地资产文件夹：在创建任何本地任务文件之前必须具备；将其作为全部任务数据根目录，并将其中的选定人物、产品和已同步参考音频视为唯一事实来源。
- 产品资产：正面、顶部、包装图片以及产品名称；产品出镜时必须提供。
- 产品替换需求：产品名称、产品表现方式、价格/行动号召（CTA），以及外观约束。
- 准确无误的口播脚本：保留用户的拼写、标点、刻意使用的谐音字以及角色标签。输入框换行仅作排版，不属于锁定口播正文，也不得直接作为分镜边界。
- 模型/工具选择：例如通过 LibTV CLI 使用 `Seedance 2.0 VIP`。
- 参考音频：当存在源参考视频并用于 Seedance KOC 生成时，参考音频应来自该源视频本身。从参考视频中提取纯音频，并将其裁剪到 `<=14.8s`，用作语气、停顿和说话节奏的参考，除非用户明确拒绝使用音频参考。用于生成时，参考音频时长必须 `<=` 视频第一个分镜/片段的时长，最好短 `0.2-0.5s`；如果使用逐片段音频变体，则每个变体的时长必须 `<=` 其目标片段时长。将其记录在标准资产部分，并将副本同步到选定的人物场景资产文件夹和产品资产文件夹，以便后续进行本地验证。
- 连贯性约束：一镜到底的感觉、可见剪辑次数上限、固定位置、皮肤/产品要求、互动风格，以及每个片段中非说话者的互动强度。

## 核心工作流

1. **深度分析源参考素材**
   - 在生成人物场景候选图、编写提示词或进行 LibTV 生成之前，为 `单人唠嗑` 和 `双人唠嗑` 任务创建一份原始参考素材深度拆解文档。
   - 将其保存为 `<task_asset_root>/analysis/deep_dive/<产品名>_原片深度拆解.md`。
   - 创建文件时，还要在与用户的对话中呈现深度拆解的关键内容：机位/构图、关系动态、产品露出次数/时机、互动逻辑，以及哪些内容必须复刻、哪些不必复刻。
   - 不要用浅层的聊天内摘要、时长检查或产品露出计数来替代此文件。在编写提示词之前，该 Markdown 文件是必需的本地交付物。
   - 深度拆解文档必须包括：机位/构图、镜头或手机拍摄质感、身体姿势、头部/肩部动作、目光、面部表情变化、手势、停顿、说话节奏、情绪曲线、产品露出逻辑、转场逻辑、应当复刻的内容，以及不应机械照搬的内容。
   - 对于 `单人唠嗑`，分析单个说话者真实的分享行为：放松的身体状态、目光从镜头移开又回到镜头、轻微迟疑、微表情、手部空闲/搁置位置、手触碰面部/产品的时机，以及手机/相机轻微呼吸感。
   - 对于 `双人唠嗑`，分析关系动态和因果互动：谁说话、谁倾听、谁先动作、主讲人如何注意到并回应，以及说话者如何回到主线。将每一个有意义的非说话者动作节拍分类为 `low_reaction`（目光、微笑、点头、轻微姿势变化）、`active_support`（清晰的手臂/手部动作、指向、递送、触碰，或暂时占据画面较大部分）或 `co_action`（两人执行同步或配对动作，例如并排比较手臂或共同展示产品）。不要默认把所有非说话者行为都设为低幅度。
   - 将源视频中承载视觉含义的每一个 `active_support` 或 `co_action` 节拍都视为强制复刻点。对其周边帧进行密集采样，并记录执行者、身体部位/手、画面侧、运动路径、开始/结束时间、重叠/遮挡、保持时长，以及它与主讲人的因果联系。
   - 将此分析作为人物场景候选图、逐片段动作设计和连贯性的基础。不要用浅层的时长/产品露出检查取代它。

2. **锁定资产**
   - 在编写最终视频提示词之前，先从人物场景检查点开始。
   - 如果用户在选择人物场景后提供当前任务的本地资产文件夹，请将该文件夹作为选定人物场景和产品资产的唯一事实来源。不要暗中使用从旧项目复制而来的产品或人物资产。
   - 不要暗中复用之前项目的人物场景图片。对于每一个新的视频生成任务，都要根据当前参考视频输出全新的人物场景候选图。
   - 默认情况下，每次调用此技能都会创建三张人物场景候选图，相似度分别为 `50%`、`60%` 和 `70%`。
   - 生图前检查当前环境是否存在 `jenvideo` 技能。若存在，必须完整读取并按该技能调用 `open/gpt-image-2` 模型生成三张候选图；不要改用其他 jenvideo 模型。若 `jenvideo` 技能或 `open/gpt-image-2` 不存在、不可调用或失败，明确向用户报告回退原因，再使用当前环境可用的图像生成技能/模型继续，并记录实际使用的技能和模型。
   - 将三张候选图保存到 `<task_asset_root>/assets/character_scene/candidates/`，有意改变身份接近程度、场景细节、构图、服装感觉、姿势和画面组成，使三张基准图不至于同质化。
   - **候选图片交付规则**：生成候选图片后，始终将它们保存到上述本地资产路径，并在聊天对话中以图片附件形式发送，供用户审阅和选择。不要只提供 URL 链接。用户必须能够直接在聊天界面看到实际图片并做出选择。
   - 候选图片仅供用户选择。不要自动选择其中一张，不要将它们上传到 LibTV，也不要继续进行视频生成，直到用户说明其选择了哪一张，并确认已将其下载到本地资产文件夹。
   - 用户报告选定的本地图片后，验证文件是否存在，计算其哈希，并将其记录为最终人物场景基准。
   - 相似度级别应控制新场景对参考视频中的人物/场景/相机/构图/服装感觉的贴近程度：较低百分比会创建更宽松、更具原创性的变体；`50%` 是中等偏宽松的过渡；`60%` 是中等相似度；`70%+` 是最接近的视觉/风格匹配，同时仍适合生成。
   - 在图片画面外清楚标注每个输出的相似度百分比。除非用户明确要求，否则不要在人物场景候选图中添加画内文字、说明文字、字幕、产品包装、徽标、价格标签或贴纸。
   - 审核每一张候选图是否符合当前的 `单人唠嗑` / `双人唠嗑` 形式、相机风格、角色数量、构图、服装和背景。
   - 生成每张人物场景候选图时，都要求领口保守且胸部有遮盖。不得生成可见乳沟、深 V 领或明显的胸部裸露。如果参考服装较为暴露，只保留相似的整体服装风格、颜色、质地和轮廓，同时降低裸露程度；切勿机械复制参考素材的裸露程度。
   - 对于 `单人唠嗑`，人物场景必须只展示一位主讲人。不得包含伴侣、第二个人、画外互动暗示或情侣构图。
   - 对于 `双人唠嗑`，人物场景必须保留与源素材兼容的关系、角色数量、相关情况下的性别，以及主讲人/非主讲人的布局。如果某个强制 `active_support` 或 `co_action` 在第一秒内开始，选定的人物场景必须已经包含或非常接近其起始姿势和手/臂布局；应淘汰遗漏该关键姿势的候选图。
   - 在提示词文档中包含清晰的 `人物场景图确认` 部分：每个已生成相似度百分比的候选状态、选定的本地路径、可用时的哈希、唠嗑形式匹配度、相机/手部匹配度，以及任何被淘汰/错误场景图片的说明。
   - 将选定资产复制到 `<task_asset_root>/assets/character_scene/selected/`；产品资产保存在 `<task_asset_root>/assets/product/`。
   - 对关键文件计算哈希并记录源路径。
   - 让标准本地资产文件夹能够自检：参考音频处理完毕后，将可用的参考音频文件复制/同步到选定的人物场景文件夹和产品资产文件夹。为同步副本使用清晰的名称，例如 `reference_audio_from_source_video_13s.mp3`，并记录原始参考音频路径、同步副本路径和哈希。
   - 如果存在错误的已选场景，请清楚地将其重命名为错误/禁止使用，而不是删除用户数据。

3. **构建提示词包**
   - 在 `<task_asset_root>/prompts/` 中创建一份 Markdown 提示词文档和一份结构化 JSON 片段计划。
   - 在提示词包靠近顶部的位置记录唠嗑形式：`单人唠嗑` 或 `双人唠嗑`。
   - 在提示词包靠近顶部的位置包含原始参考素材深度拆解文档或指向该文档的链接，并将其结论带入全局提示词和每一个逐片段提示词。
   - 只有在选定的人物场景图片已在当前任务本地资产文件夹中得到确认后，才构建提示词；除非用户明确要求无资产初稿。提示词包必须声明正在使用哪个本地资产文件夹。
   - 将提示词包交给用户确认时，包含一份已就绪可供提示词使用的资产审计：文件是否存在、可用时的哈希、资产角色、片段用途、参考音频的时长/编解码器，以及产品可见的分镜编号。此项审计不能替代用户批准后最终进行的“脚本已确认”本地资产复查。
   - 在提示词包靠近顶部的位置记录人物场景候选/选择状态。如果用户尚未选择一张本地候选图片并下载，请将视频生成标记为阻塞，等待用户确认。
   - 用户在新口播输入框中的换行只属于排版，不是分镜指令。禁止按用户换行数量决定分镜数量，也不得因漏换行、空行或错误换行阻塞任务；先规范化排版换行，再锁定逐字、逐标点口播全文。
   - 先从原片深度拆解中提取真实镜头切点、镜头功能、动作因果、情绪和转场，再结合新口播的语义推进重新规划新分镜数量与逐段口播。分镜必须能够回溯到对应的原片结构镜头，不能只按字符数或标点机械等分。
   - 将重新规划后的脚本拆分为时长 <=15s 的片段，并准确保留口播文本；所有逐段口播按顺序拼接后必须与规范化锁定全文完全一致。
   - 根据新口播的字符数据，按其与参考视频的比例设置新视频的总时长，然后在提示词包中记录计算过程和假设。不要盲目使用固定总时长、固定 7 个片段或固定的逐片段时长。如果无法获得原始参考素材的准确文字稿，则根据源视频深度拆解估算参考素材的语速密度，并说明该估算。
   - 默认逐片段时长目标：在脚本和用户目标允许的情况下，将每个生成的分镜片段保持在约 `12-14.5s`；避免过短的片段，除非用户明确要求更短的总片长、源参考素材有此要求，或片段脚本太短，无法自然支撑 12 秒。
   - 包含以下逐片段字段：片段编号、时长、任务、产品可见性、必需资产、场景/人物一致性、产品一致性、内容、从 `0s` 开始计时的动作、口播、负面提示词。
   - 在任何 LibTV 生成开始之前，对每个生成的分镜片段，都要在 Markdown 提示词包和结构化 JSON 片段计划中保存一个 `final_libtv_prompt` 字段。JSON 中的该字段是计划传给 LibTV `--prompt` 的唯一机器可执行事实来源。
   - `final_libtv_prompt` 必须合并全局连贯性控制、源参考素材结论、逐片段口播、定时动作、产品/手部/相机规则、负面提示词、尾帧/首帧规则，以及具体的本地资产角色。如果视频模型需要某些关键生成指令，就不要让这些指令只存在于独立章节中。
   - 不要手写 CMD/PowerShell 命令来复制提示词，也不要在执行时临时组装一个存在实质差异的提示词。如果上传后运行时细节发生变化，例如实际 LibTV 节点显示名称、已上传的参考音频标签、尾帧资产名称或时长变化，请先更新 Markdown 和 JSON 中的 `final_libtv_prompt`。
   - 在支持 PowerShell 的交互式 Skill 执行环境中，LibTV 节点创建、提示词核验和最终并发生成必须使用技能自带脚本：`scripts/invoke-libtv-clip-plan.ps1` 负责单分镜节点创建与严格核验；`scripts/invoke-libtv-clip-plan-parallel.ps1` 负责先核验全部分镜，再同时触发全部节点生成。视频平台服务端运行于不含 PowerShell 的 Linux 容器时，允许使用平台内置的跨平台编排器，但必须执行完全相同的两阶段契约：第一阶段顺序创建全部节点并严格核验提示词，第二阶段才并发启动全部节点。无论使用哪种编排器，任何提示词差异都必须中止，禁止自动继续。
   - 在提示词文档的标准资产部分，明确列出 `reference audio`：源参考视频、提取/裁剪规则（`pure audio`、`<=14.8s`，并且用于生成时 `<=` 第一个分镜/片段时长，最好短 `0.2-0.5s`）、主要本地路径、人物/产品文件夹中的已同步本地副本、哈希、时长/编解码器/采样率/声道，以及可用时的 LibTV 音频节点。
   - 使用 Seedance 音频参考时，将 `reference_audio` 添加到每个片段的必需资产中。
   - 在每一个逐片段提示词中重复全局连贯性控制，不要只写在全局章节中。
   - 将所有片段视为一条完整 KOC 唠嗑视频中相互连接的段落。用户的最终交付物是拼接后的完整视频，而不是互相独立的短片。逐片段提示词必须保留与参考素材相连的情绪、动作表现、说话节奏、同人同景连贯性，并且必须在每个片段的开头和结尾设计自然转场。
   - 避免片段之间产生硬切感：只要可能，每个片段都应继承前一个片段的目光、姿势、手部位置、产品位置、情绪节拍或句子势头。
   - 在每个逐片段提示词中明确说明：口播结束后，只保留 `0.2-0.3s` 的自然收尾表情用于拼接；不要仅为填满要求时长而添加只有停顿的空镜、人物定格停留、无声填充表情、无效手势或额外动作。
   - 除非用户明确要求，否则不要要求模型在视频画面中添加字幕、说明文字、标题卡、贴纸文字或对话文字叠层。添加如下负面提示词：`不要字幕，不要口播字幕，不要画面叠字，不要新增标题文字，不要贴纸文字；产品包装自带品牌文字除外`。
   - 对于每一个 KOC 口播片段，明确写出相机/手部逻辑：使用 `固定机位拍摄，不存在持机手，展示产品/摸脸/摸眼周都由自然空闲手完成`，或者使用 `固定左手/右手持机，持机手不进入画面，所有展示产品/摸脸/摸眼周/指向动作都由另一只不持机的手完成`。
   - 如果片段需要复杂的产品展示、打开包装、触碰面部或眼周演示，优先使用固定机位。如果使用手持相机，绝不能要求画面中可见的手既拿手机又执行动作。
   - 对于 `单人唠嗑`，重点表现一位说话者真实的分享节奏：与镜头进行眼神交流、轻微迟疑、手势、面部反应、目光转向产品/手/侧面，以及手机/相机稳定性。不要凭空加入第二个人、画外对话、伴侣反应或双人互动节拍。
   - 对于 `双人唠嗑`，保留真实的源素材关系和说话角色；主讲人承担旁白，而非说话者可以是任何性别的伴侣、亲属、朋友或同事。
   - 在每个包含双人互动的片段中添加 `interaction_mode` 和带时间信息的 `non_speaker_action_track`。严格使用深度拆解中分类的 `low_reaction`、`active_support` 或 `co_action`。
   - 对于 `low_reaction`，让动作保持细微且具有因果关系，同时不要让非说话者变成第二位主持人。对于 `active_support` 和 `co_action`，不要添加相互冲突的一刀切约束，例如 `低幅度`、`不抢画面中心`、`不接触产品` 或 `保持静止`，除非源动作节拍本身要求这样做。
   - 对于每一个强制 `active_support` 或 `co_action`，写出带时间信息的动作几何：谁移动、哪条手臂/哪只手/哪个身体部位移动、其画面侧位置和路径、与镜头的距离、重叠顺序、保持时长，以及另一个人同时在做什么。明确说明不得遗漏该动作，也不得用被动反应替换它。
   - 当强制动作节拍包含靠近相机的多手重叠或同步肢体动作时，如果模型支持，请使用源视频作为动作参考；否则，连接密集的关键动作帧，并使用一张包含起始姿势的选定人物场景。不要只依赖笼统的文字。
   - 对于任何双人互动段落，在编写提示词之前，先对源视频中该段落周围进行更密集的帧采样检查。捕捉谁看谁、谁先移动、谁做出反应、微笑/点头/转身的时机、距离变化、打断点，以及说话者如何回到主线。
   - 将互动分析转换为带时间信息的提示词节拍。不要只写 `自然互动` 这样的笼统短语；要明确因果互动，例如：`非主讲人听到这句后先笑，主讲人停半拍转头看对方，再笑着回应，然后转回镜头继续讲`。

4. **产品露出确认检查点**
   - 原片逐镜深拆必须为每个源镜头记录 `productVisible` 与 `productEvidence`；新分镜映射到任何产品可见的源镜头时，必须自动标记为产品露出，并以用户上传的目标产品素材替换原片产品。用户手填的新视频露出分镜只作为额外补充，不能因为留空而丢失原片产品露出。
   - 根据新口播脚本输出或更新视频提示词后，在进行任何视频生成之前审核产品可见性。
   - 明确告知用户：
     - 产品在参考视频中出现了多少次，按连续可见的露出段落计数。
     - 产品在新视频提示词中出现了多少次。
     - 新提示词中展示产品的准确片段/分镜编号。
   - 将此作为一个快速手动质量保证检查点，以便用户定位并确认产品露出频率。
   - 在用户确认产品露出次数和分镜编号可以接受之前，不要开始 LibTV 视频生成。

5. **处理参考音频**
   - 使用 `ffprobe` 检查时长、流、编解码器、采样率和声道。
   - AI-KOC 参考音频统一生成 `.mp3`：`libmp3lame`、192 kbps、44.1 kHz、双声道。上传 LibTV 前必须再次使用 `ffprobe` 强制确认扩展名为 `.mp3` 且音频编码为 MP3，同时复核码率、采样率、声道、文件哈希和时长；不得上传 M4A/AAC 变体。
   - 如果参考素材是视频或时长超过 14.8 秒，则从参考视频本身提取纯音频，并裁剪到 `<=14.8s`，作为源语气、停顿和说话节奏的参考。
   - 分镜时长确定后，创建一份可安全用于生成的参考音频文件，其时长应 `<=` 视频第一个分镜/片段的时长，最好短 `0.2-0.5s`。例如，对于 10 秒的第一个片段，应使用约 9.5-9.8 秒的音频，而不是 14.8 秒。
   - 如果不同片段使用不同的目标时长，并且按片段连接 Seedance 音频参考，请创建逐片段或按时长分桶的音频变体，使每个上传的音频节点时长都 `<=` 该片段的 `duration` 参数，最好短 `0.2-0.5s`。
   - 在可能的情况下使用 `scripts/prepare-reference-audio.ps1`。分镜时间确定后，传入 `-TargetClipDuration <seconds>`；该脚本会将输出限制在 `14.8s`，以及 `TargetClipDuration - SafetyMargin`（默认余量为 `0.3s`）之内。
   - 创建可用音频文件后，将其同步/复制到选定的人物场景资产文件夹和产品资产文件夹中，以便后续检查可从任一文件夹验证本地标准资产。
   - 将处理后的音频作为 LibTV `audio` 上传，不要将其作为视频参考上传，除非模型明确要求视频。

6. **脚本已确认后的本地资产复查**
   - 在提示词包连同其已就绪可供提示词使用的资产审计一起输出、并经用户确认后，执行此步骤。这是任何 LibTV 上传或生成之前的最终关卡。
   - 用户确认脚本/提示词包后，在进行任何 LibTV/Seedance 视频生成之前，执行第二次本地资产检查。
   - 复查标准本地文件夹和清单：产品资产、选定的人物场景、参考音频主文件、人物/产品文件夹中的已同步参考音频副本、哈希、文件是否存在，以及当前每个片段的必需资产。
   - 在将任何人物场景资产上传到 LibTV 之前，目视检查选定图片的领口是否保守、胸部是否有遮盖。如果图片显示或可能显示可见乳沟、深 V 领或明显的胸部裸露，请通知人工审核者，并暂停上传，等待人工决定。不要暗中上传，也不要自动重新生成资产。
   - 确认可安全用于生成的参考音频时长 `<=` 第一个分镜/片段时长，最好短 `0.2-0.5s`；对于逐片段音频变体，确认每个变体的时长 `<=` 其目标片段时长。
   - 确认当前 LibTV 画布是此任务预期使用的画布，而不是之前遗留的旧测试画布。
   - 确认准确的逐片段口播仍与已锁定脚本一致，并且产品露出规则仍然正确。
   - 在完成此本地标准资产复查之前，不要开始视频生成。将任何缺失、陈旧或不匹配的资产报告为阻塞项。

7. **准备 LibTV**
   - 对于 LibTV 项目、画布、节点、上传、生成和下载，只使用 `libtv-cli` 技能和 `libtv` CLI。
   - **身份验证检查**：进行任何 LibTV 操作之前，运行 `libtv account info`。如果返回 401 或“未登录”，请遵循上方身份验证规则运行 `libtv login web --open`。只有登录失败时才通知用户人工关闭代理/VPN后重试。
   - 确认 CLI 登录状态和当前 `.libtv/project.json`。
   - 创建或选择用户要求的工作区/项目/画布。
   - 只将已确认、与当前任务兼容的人物场景、产品资产和处理后的参考音频作为资源节点上传。对于双人任务，不要上传陈旧的单人图片；对于单人任务，也不要上传陈旧的双人图片，除非用户明确批准。
   - 交互式 Skill 执行使用 `scripts/invoke-libtv-clip-plan-parallel.ps1 -ClipPlanPath <绝对JSON路径>` 执行整份片段计划；Linux 视频平台使用内置跨平台两阶段编排器。禁止逐个“创建即运行”，也不得在全部节点提示词严格核验完成前开始任一分镜生成。
   - 并发脚本第一阶段必须按分镜顺序创建节点并严格核验：从 JSON 读取每个 `final_libtv_prompt`，以单个参数原样传给 `--prompt`，然后查询节点并与 `data.params.prompt` 比较。仅允许 CRLF/LF 换行归一化；任一分镜存在其他字符差异时，停止整批流程，一个分镜都不得开始生成。
   - 全部分镜节点核验通过后，第二阶段必须为每个分镜启动一个独立的 `libtv node <nodeKey> --run` 阻塞进程，并在等待前先启动全部进程，使所有分镜并发生成。不要把多个进程接到同一条 NDJSON 管道；每个分镜分别写 stdout/stderr 日志。
   - 每个 `libtv --run` 进程自行同步等待终态；并发编排层只等待各进程退出，不自行轮询 taskId，不因看到中间进度就提前结束。
   - 将顺序创建、查询、提示词一致性校验以及各分镜并发运行结果保存到 `<task_asset_root>/libtv/logs/`，并在 `<task_asset_root>/libtv/state/parallel_run_summary.json` 汇总每个节点的开始时间、结束时间、退出码和成功状态。

8. **生成片段**
   - 运行任何生成命令之前，验证产品露出检查点已经报告给用户并获得明确批准。
   - 将最终生成视为一个并发批次：只有全部节点的资产、时长和 `final_libtv_prompt` 都通过预检后，才一次性并发启动所有分镜。不要在校验下一个分镜时提前运行前一个分镜。
   - 某个并发分镜失败时，允许其他已启动分镜继续等待终态；整批结束后统一报告成功/失败清单。不要因单个失败取消已在运行的其他分镜，也不要自动重复提交失败分镜。
   - 使用用户准确要求的模型名称，例如 `-s "model=Seedance 2.0 VIP"`。
   - 对于 Seedance 2.0 混合参考，设置 `modeType=mixed2video`、`ratio=9:16`、时长低于 15 秒，并设置 `enableSound=on`。
   - 在每次带音频参考运行 Seedance 之前，验证已连接音频节点的时长 `<=` 该生成片段的目标 `duration`。如果整条视频共用一份音频参考，使其时长 `<=` 第一个分镜/片段时长，最好短 `0.2-0.5s`。如果音频更长，请先裁剪并重新上传再运行；过长的音频可能导致任务在 99% 等高进度处停滞。
   - 如果连接音频后，某次运行在接近 99% 处停滞，首先将音频裁剪到比目标片段时长更短，然后重试。如果缩短音频后仍然无法输出成功视频，请停止添加重复的诊断性生成任务，清楚地报告阻塞项，并移交人工处理。
   - 对于普通 KOC 口播片段，优先使用 `duration=12` 到 `duration=14` 或 `14.5`，使片段不至于太短，但要避免过度填充：如果口播很短，应指示模型以自然且稍快的 KOC 节奏说话并干净利落地结束，而不是用无声停留填满时间。
   - 如果 Seedance 合规检查阻止生成：
     - 验证人物图片是否具有 `assetId`/肖像资产元数据。
     - 如果 LibTV 支持，将非人物产品图片标记为合规/豁免。
     - 在不使用音频的情况下进行测试，以隔离音频是否为阻塞原因。
     - 如果音频是阻塞原因，请将其裁剪为 <=15s 的纯音频并重新上传。
   - 保留旧的失败/测试节点，除非用户要求删除它们；清楚命名测试节点。

9. **验证输出**
   - 使用 `libtv download -n <node> -o <task_asset_root>/outputs/clips --without-ai-watermark --vip` 下载已完成的视频。运行前必须通过 `libtv account info` 确认 `activeAccount.memberAccount.effective=true`；`--without-ai-watermark` 请求去 AI 水印原链，`--vip` 明确启用会员下载策略。若无法确认有效会员资格，不得虚假声明 `--vip`，应报告去水印资格阻塞项。下载后仍需检查实际画面，不要虚假承诺一定无水印。
   - 始终将成功生成的视频保存在 `<task_asset_root>/outputs/clips/<clip_no>_<task>_<model>.mp4`；不要让成品视频只留在远程 LibTV 节点上。
   - 运行 `ffprobe`，确认视频流/音频流、时长和分辨率。
   - 在每个成功的分镜片段都已下载并通过 `ffprobe` 后，自动使用本地片段创建一条完整时长的预览视频。按分镜编号排序，在 `<task_asset_root>/intermediate/concat_<canvas_or_workspace_name>.txt` 写入不带 BOM 的 UTF-8 拼接列表，然后运行 `ffmpeg -y -f concat -safe 0 -i <concat_list> -c copy <task_asset_root>/outputs/final/<canvas_or_workspace_name>_全片拼接预览版.mp4`。
   - 使用 `ffprobe` 验证完整时长预览。保持单独下载的片段不变；如果文件不兼容，导致 `-c copy` 无法生成有效预览，请报告拼接失败，不要暗中重新编码，除非用户批准采用其他方法。
   - 检查生成的视频中是否存在可见乳沟、深 V 领或明显的胸部裸露。如果出现其中任何一种情况，请通知人工审核者，并记录受影响的片段和大致时间戳或帧。是否需要重新生成只能由人工审核者决定；不要自动重新生成，也不要在做出该决定之前将视觉审核标记为通过。
   - 将每一个强制 `active_support` 和 `co_action` 与其参考关键帧和带时间信息的动作轨道比较。如果动作缺失、被弱化为被动反应、分配给错误的人/肢体，或丢失必需的并排/重叠关系，请将互动复刻标记为失败，并运行一次以动作为优先的定向重试。如果两次定向尝试后仍然遗漏同一个强制动作，请停止自动重试，通知人工审核者；只有在人工指示下，才能转入人工专项生成或人工结果选择。
   - 报告准确的本地路径，以及任何已知的模型偏差。
   - 除非已经检查实际输出，否则不要在没有用户审阅的情况下声称脚本或风格生成成功。

## KOC 连贯性规则

对于每一个片段提示词，重复一段简洁的连贯性规则块：

- 将该片段视为完整视频的一个段落，而不是独立短片。
- 使用同一部手机、相同的手持/固定机位逻辑、相同距离、相同光线、相同背景、相同服装、相同人物位置。
- 在整个片段中，让每个人物的领口保持保守、胸部保持遮盖；不要让动作生成降低领口，或引入可见乳沟、深 V 领或明显的胸部裸露。如果参考服装较为暴露，只保留相似的整体风格，同时降低裸露程度，不要机械照搬。
- 选定的人物场景必须与唠嗑形式匹配：`单人唠嗑` 使用单人基准，`双人唠嗑` 使用情侣/搭档基准。
- 保留真实分享感：随意的居家聊天节奏、自然的轻微迟疑、有生活感的反应，以及对话中的信任感。避免带货主播式表达、脚本化广告表演、过于完美的手势或僵硬的产品演示。
- 对于双人唠嗑视频，保留参考素材中的关系和说话角色，而不要假设他们一定是男女情侣。主讲人承担旁白；非说话者保持因果性的回应，并且在参考素材要求时，可以执行视觉上显眼的动作。
- 重复该片段的 `interaction_mode` 和带时间信息的 `non_speaker_action_track`。仅对 `low_reaction` 应用低幅度/不居中的措辞；对于 `active_support` 和 `co_action`，允许必需的画面占比、接触、手臂伸展或同步运动。
- 将强制的并排比较、共同展示、递送、触碰以及其他配对动作视为核心连贯性，而不是可有可无的装饰。保留执行者身份、肢体分配、画面侧、运动路径、重叠顺序和保持时长。
- 双人互动必须具有因果关系并带有明确时间：倾听者的反应跟随某句具体台词，说话者注意到或回应，然后回到主镜头/故事。避免使用没有明确节拍的模糊 `natural interaction`（“自然互动”）措辞。
- 相机逻辑必须在物理上合理。使用固定的手机/三脚架/桌面相机，或由一只固定的手拿着手机。持机手绝不能出现在画面中。
- 需要产品展示、触碰面部、指向眼周、开盖或其他可见动作时，必须由非持机手完成。对于固定机位片段，任意一只手都可以自然执行动作。
- 避免不可能的手部逻辑：不能有多余的手，不能让同一只手同时拿手机和产品，也不能因为本应持机的手发生动作而导致相机突然跳动。
- 保持一镜到底的感觉；可见剪辑次数 <= 用户限制。
- 每个片段结尾只保留 0.2-0.3 秒稳定自然的表情，用于拼接。
- 不要让片段尾部在口播结束后变成无声空镜、人物定格停留、无效填充手势或额外动作。
- 保持皮肤对比和角色行为：主讲人在前，搭档在后，自然进行眼神交流并做出反应。
- 产品只在指定片段中出现，并且必须符合物理现实。
- 默认不添加画面字幕或文字叠层；仅在要求产品可见时保留产品包装文字。
- 口播必须像已经背熟一样自然、富有交流感，而不是照稿朗读。

## 准确脚本处理

将用户提供的口播文案视为已经锁定的产物：

- 不要规范化姓名、谐音字、品牌拼写、标点或角色标签。
- 如果用户写了诸如 `琴海路` 或 `海路姐` 这样的刻意变体，请原样准确保留。
- 编辑提示词或 JSON 后，拼接所有片段的口播，并与用户脚本进行比较。
- 完成替换后搜索是否仍有陈旧术语残留。

## Seedance 2.0 音频说明

Seedance 可能会因为一些看起来像通用合规失败的原因而拒绝参考音频。实用诊断方法如下：

- 已上传音频如果超过 15 秒，仍然可能失败。
- 带音轨的 MP4 不能直接作为 AI-KOC 音频参考上传；必须先提取为纯 MP3。
- 一个可用的源音频标准是：`.mp3`、MP3 编码（`libmp3lame`）、192 kbps、44.1kHz 立体声、`<=14.8s`、>1.8s。用于生成时，优先使用 `min(14.8s, first_clip_duration - 0.2s to 0.5s)`；对于逐片段参考，使每个音频文件都短于该片段时长。
- 如果 `autoCompliance=1` 阻止生成，但图片已经合规，请运行一次无音频测试；如果成功，则修复音频。
- 如果 `autoCompliance=0` 返回提及时长的任务失败，或者连接音频后某次运行在接近 99% 处停滞，请先将音频裁剪到低于目标片段时长，然后重试。如果缩短音频后仍无法输出成功视频，请停止反复重试，清楚报告阻塞项，并移交人工处理。

## 输出

交付最精简且实用的一组内容：

- Markdown 提示词文档，放在 `<task_asset_root>/prompts/` 下。
- 每个提示词包都需要一份结构化片段计划 JSON；这是必需的，因为每个片段的 `final_libtv_prompt` 和准确口播必须在生成前保存并检查。
- 原始参考素材深度拆解文档，例如 `<task_asset_root>/analysis/deep_dive/<产品名>_原片深度拆解.md`，内容涵盖相机、动作、表情、手势、停顿、产品露出逻辑、可复刻点，以及不应机械照搬之处。
- 人物场景检查点：`50%`/`60%`/`70%` 三张候选图的状态、实际生图技能/模型、最终由用户选定并下载的图片路径、可用时的哈希、唠嗑形式匹配度，以及用户确认状态。
- 已就绪可供提示词使用的资产审计：当前本地资产文件夹、文件是否存在及其哈希、资产角色、逐片段用途、音频属性，以及产品可见的分镜。
- 服装裸露审核检查点：候选图保守领口状态、上传前目视检查状态，以及任何生成视频的人工审核通知；其中应包含受影响的片段/时间戳和可用时的人工重新生成决定。
- 对于 `双人唠嗑`，提供非说话者互动检查点：记录每个互动片段的 `interaction_mode`、强制动作节拍、执行者/肢体/时间/几何、源关键动作参考、提示词冲突审计，以及输出通过/定向重试/人工审核状态。
- 产品露出检查点：参考视频露出次数、新提示词露出次数、产品可见的分镜/片段编号，以及用户是否批准生成。
- 处理后的参考音频路径和已上传的 LibTV 节点名称。
- 选定人物场景文件夹和产品资产文件夹中的已同步参考音频副本路径。
- 脚本已确认后的本地资产复查状态。
- LibTV 工作区/画布 URL 和节点名称。
- LibTV 提示词一致性检查点：每个片段的本地 Markdown `final_libtv_prompt`、JSON `final_libtv_prompt`、节点 `data.params.prompt`，以及通过/已修正状态。
- LibTV 并发运行摘要：全部分镜的并发启动状态、每个节点的开始/结束时间、退出码、独立 stdout/stderr 日志路径，以及整批成功/失败清单。
- LibTV 下载去水印记录：每个片段是否在有效会员账号下同时使用 `--without-ai-watermark --vip`，账号是否具备原链资格，以及实际文件的水印检查结果。
- 已生成视频的文件路径和 ffprobe 验证摘要。
- 完整时长拼接预览路径和 ffprobe 验证摘要。
- 对阻塞项的清晰解释，尤其要区分模型可用性、模型合规性和媒体时长失败。
