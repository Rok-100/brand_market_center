# 一键做同款：历史制作分类治理 v1

## 目标

允许“历史任务做同款”中的模板归属人和实名管理员修正制作分类。分类修正后，历史卡片、后续做同款任务、共享 OSS 快照、数据库结构化字段与检索正文必须使用同一分类；已生成的视频文件保持不变。

## 单一事实源

- 制作分类的权威字段为案例 JSON 中的 `changeType`，只接受服务端 `CHANGE_TYPES` 中的六个固定 ID。
- `audit.videoType`、分类标签、`audit.assets[].rebuildRoles`、`rebuildRequired`、`generationRequired` 和 `replacementStrategy` 都由新 `changeType` 与既有逐图事实重新计算，不接受前端直接写入。
- `sourceSnapshot.orderedAssets` 中的处理路由同步跟随审计结果更新，避免历史卡片显示一种分类、快照恢复又按旧分类执行。
- 每次修改记录 `changeTypeUpdatedAt`、`changeTypeUpdatedBy` 和最近 20 条 `changeTypeHistory`。

## 权限

- 模板归属人只能修改自己名下的案例。
- 一键做同款实名管理员可跨归属修改。
- 共享历史中的其他普通用户只有查看和做同款权限，不显示“修改分类”，后端也必须返回 403。

## 同步协议

前端调用：

```http
PATCH /api/one-click-remake/history/:recipeId/change-type
Content-Type: application/json

{
  "changeType": "product_voiceover",
  "expectedChangeType": "product"
}
```

- `expectedChangeType` 用于阻止页面停留期间的并发覆盖；服务端发现当前分类已变化时返回 409，前端要求刷新后重试。
- 服务端校验权限和快照事实完整性后，生成新不可变 JSON 快照，更新 OSS 对象、数据库 `change_type`、`video_type`、`tags_json`、`search_text`、`recipe_json` 和本机回退记录。
- 新数据库索引写入成功后才清理旧 OSS 快照。任一存储返回警告时，前端展示真实同步状态，并重新请求历史列表，不用本地乐观值冒充成功结果。

## 历史快照复用

- 修改分类不重新读取源 LibTV 账号、源画布或源节点，也不重新调用 Qwen 审计。
- 平台保留逐图识别得到的 `productBearing`、`backgroundBearing`、`personBearing` 等事实，仅根据新分类重算处理路由。
- 新分类需要的逐图事实缺失时拒绝修改，并提示重新归档模板，禁止在证据不足时猜测。
- 已生成成片关联的源模板即使仍保存旧分类，只要事实完整，创建新任务时也会按所选新分类重算审计派生字段，避免关联源模板阻断修正后的制作单元。

## “仅换产品”修正为“换产品 + 口播”

1. 归属人或管理员在历史卡片点击“修改分类”，选择“换产品 + 口播”。
2. 保存成功后重新加载历史列表，卡片标签与“使用共享快照做同款”按钮参数统一变为 `product_voiceover`。
3. 点击做同款后恢复共享拆解快照；产品承载图继续按换品路由处理，不重复拆解源画布。
4. 在目标 SKU 的“新视频提示词（含新口播文案）”中修改说话人、逐字台词与顺序，再确认资产并重新生成视频。
5. 新结果按 `product_voiceover` 归档；原历史视频文件不覆盖，便于审计与回退。
